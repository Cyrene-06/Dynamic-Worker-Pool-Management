## 1. 背景与问题定义

Agent（智能体）类负载与普通微服务有本质差异，导致现有 Kubernetes 原语**不匹配**：

| Agent 负载特征 | 与 K8s 默认行为的冲突 |
|---|---|
| 会话短、创建频率高、突发强 | Pod 创建含调度 + 拉镜像 + 启动，秒级；`ReplicaSet` 只做水平扩缩不支持"按需认领" |
| 需要**强隔离**（执行任意 LLM 生成代码） | 默认 runc 共享内核，容器逃逸即节点失守 |
| 生命周期为「分钟～小时」且可能长时间空转 | 无 TTL 概念；空闲 Pod 长期占资源 |
| 有状态（工作目录、已加载依赖、会话内存） | 无原生「休眠/唤醒」；重建成本高 |
| 会话与沙箱一一绑定，不能复用 | Service/LoadBalancer 是"共享"语义，与 1:1 认领冲突 |
| 失败即丢弃，可重启 | 但若无人回收会形成**资源泄漏** |

一句话：**K8s 擅长管理长期存在的服务，不擅长管理海量短生命周期、需强隔离、有状态、需精确回收的沙箱。**

## 2. 典型业务场景

| 场景 | 沙箱形态 | 关键诉求 | 资源画像 |
|---|---|---|---|
| S1 代码解释器 | Python/Node 容器，只读根 + 临时盘 | 秒级拉起、注入用户代码、执行完销毁 | CPU 突发、内存小（256–1Gi） |
| S2 浏览器 Agent | Chrome + 无头桌面 | 强隔离、较长会话（10–60min）、内存大 | 内存 2–4Gi、CPU 低 |
| S3 数据分析 Agent | 带数据集的多步任务 | 长任务（小时级）、可挂载大卷、可中断恢复 | CPU/IO 密集、内存中高 |
| S4 长对话 Agent | 常驻进程 + 会话状态 | 长驻、频繁空闲、需快速唤醒 | 内存常驻、CPU 长期空转 |

> 设计必须同时覆盖 **S1 的高频短生命周期** 和 **S3/S4 的长驻空闲**，这两个极端决定了架构上限。

## 3. 功能性需求

| ID | 需求 | 说明 |
|---|---|---|
| FR-1 | 声明式沙箱申请 | 业务方提交 `AgentSandbox` 对象即可获得可用沙箱，无需感知 Pod/调度/网络细节 |
| FR-2 | 沙箱池化与预热 | 支持配置 `SandboxPool` 维持 N 个 Ready 库存；申请时「认领」而非创建 |
| FR-3 | 完整生命周期状态机 | `Pending → Provisioning → Ready → Running → Idle → Hibernating → Hibernated → Terminating` |
| FR-4 | 自动回收 | TTL 超时、空闲超时、空闲占比超阈、租户删除 四类触发 |
| FR-5 | 资源泄漏防护 | 任何异常路径（节点失联、Operator 崩溃、Pod 被手动删除）都不产生孤儿资源 |
| FR-6 | 会话保活与心跳 | 业务方可续租；心跳丢失按策略告警或回收 |
| FR-7 | 休眠与恢复 | 空闲沙箱可进入低资源占用状态并快速恢复（业务无感） |
| FR-8 | 强隔离运行时 | 通过 `RuntimeClass` 选择 runc / Kata-Firecracker |
| FR-9 | 出网与入网治理 | 默认拒绝 + 显式白名单；沙箱不可访问 API Server |
| FR-10 | 优先级与抢占 | 高优先级（交互式）可抢占低优先级（批处理）的池内库存 |
| FR-11 | 池运维接口 | 池水位可观测、可手动扩缩、可 drain（排空用于升级） |
| FR-12 | 配额与限流 | 按租户限制并发沙箱数与总资源；超限时快速失败而非排队雪崩 |
| FR-13 | 沙箱业务接口 | 申请/续租/释放/查询状态/获取接入信息（hibernate/wake 可选暴露） |
| FR-14 | 审计 | 谁在何时申请了何规格沙箱、执行了什么镜像、访问了哪些出口 |

## 4. 非功能需求（SLO）

### 4.1 延迟

| 指标 | 目标 | 测量点 | 备注 |
|---|---|---|---|
| 热路径申请延迟 P95 | **< 800 ms** | 提交 CR → 返回可用沙箱接入信息 | 池命中路径 |
| 热路径申请延迟 P99 | < 1.5 s | 同上 | |
| 冷路径申请延迟 P95 | < 2.5 s | 池空时全新建 | 含调度 + 镜像（假设节点镜像预热） |
| 唤醒延迟（Hibernated → Ready）P95 | L1/L2 < 1.5 s；L3 快照恢复 < 300 ms | — | L3 依赖 Firecracker 快照 |
| 池命中率 | **> 90%**（稳态） | 热路径数 / 总申请数 | 低峰可放宽 |
| 空闲识别延迟 | < 30 s | 最后活动 → 判定 Idle | |
| 空闲 → 资源释放 | < 60 s | 判定 Idle → 内存实际归还 | 含 L1 冻结 |

### 4.2 容量与规模（设计目标，需压测校正）

| 维度 | 目标 |
|---|---|
| 单集群并发沙箱数 | 5,000（混合：80% 短生命周期 + 20% 长驻） |
| 峰值创建速率 | 200 沙箱/秒（依赖预热池，冷路径仅兜底） |
| 峰值回收速率 | 300 沙箱/秒（批量回收需限速，见 `05` 文档） |
| 单节点沙箱密度 | runc 模式 ≥ 40 个；Kata-FC 模式 ≥ 30 个（4C8G 节点） |
| 控制面自身开销 | Operator 内存 < 512Mi，CPU < 1 core（5k 对象规模） |
| API Server 写入放大 | 稳态 < 50 write QPS |

### 4.3 可用性

| 指标 | 目标 |
|---|---|
| 控制面可用性 | 99.9%（Operator 多副本 + Leader Election） |
| 沙箱可用性 | 99.5%（不含节点故障导致的必然丢失） |
| 节点故障影响面 | 仅影响该节点上的沙箱；业务方按「沙箱可丢弃」设计 |
| 回收准确性 | 泄漏率 0（无孤儿 Pod/Lease/NetworkPolicy/Volume） |
| 误杀率 | < 0.1%（活跃会话被回收的比例） |

### 4.4 资源效率

| 指标 | 目标 |
|---|---|
| CPU 有效利用率 | > 55%（Σ 实际用量 / Σ 节点可分配） |
| 内存有效利用率 | > 65% |
| 内存超卖比上限 | 1.5x（仅对可重启沙箱） |
| 装箱碎片率 | < 10%（因 requests 过大导致无法调度的资源占比） |
| 单沙箱控制面成本 | < 0.5% 的沙箱资源（即 512Mi Operator 管理 5k 沙箱） |

### 4.5 可维护性

- **可测试性**：控制逻辑必须能在无 KVM 的本地环境（kind + envtest）完整验证。
- **可升级性**：CRD 需支持版本演进（`v1alpha1 → v1beta1`），字段只增不删。
- **可观测性**：所有状态迁移必须有指标与事件，不允许"黑盒回收"。

## 5. 约束条件

| 类型 | 约束 | 影响 |
|---|---|---|
| 硬件 | Kata + Firecracker 需 `/dev/kvm`（裸金属或支持嵌套虚拟化的实例） | 云上需选 `*.metal`；本地 kind 无法真跑 |
| 本地开发 | kind 节点是 Docker 容器，嵌套虚拟化链路脆弱 | 必须提供 `simulated` 隔离模式 |
| 内核 | Firecracker 需要较新内核；需开启 `KVM`、`vhost`、`overlay`、`cgroup v2` | 节点镜像需定制 |
| K8s 版本 | 建议 ≥ 1.30（依赖 `RuntimeClass` 稳定、`InPlacePodVerticalScaling` beta） | 见 `02` 文档 |
| Firecracker 能力 | 无 PCI / 无 GPU / 无任意设备模拟，仅 virtio-net/block/fs/vsock | 排除 GPU 沙箱场景 |
| 生态 | Kata 与部分 CNI/CSI 组合兼容性需验证 | 见 `06` 文档兼容性矩阵 |
| 组织 | 需业务方接受「沙箱可能被回收」的语义 | 影响 API 契约设计 |

## 6. 非目标（Non-Goals）

明确排除，避免范围蔓延：

1. **不实现 Agent 推理编排**（工具调用、Prompt 管理、记忆存储）。
2. **不改造 Kubernetes 本体**（不 fork kube-scheduler / kubelet）。
3. **不支持 GPU / 加速器直通的沙箱**（Firecracker 无法 PCI 直通；如需请另立方案）。
4. **不做跨集群联邦调度**（单集群设计，多集群靠上层路由）。
5. **不做沙箱内业务进程的细粒度观测**（仅注入 sidecar/OTel 采集，不侵入 Agent 框架）。
6. **不追求零停机节点升级下的沙箱迁移**（VM 级迁移超出范围，采用 drain + 重建）。
7. **不做通用多租户 SaaS 计费系统**（仅提供用量指标，计费由外部系统消费）。

## 7. 术语表

| 术语 | 含义 |
|---|---|
| **Sandbox** | 一个隔离的执行环境，K8s 中表现为 `AgentSandbox` CR + 1 个 Pod |
| **Warm Pool** | 预先创建并处于 Ready 状态、尚未被认领的沙箱库存 |
| **Claim（认领）** | 将池中空闲沙箱**排他地**绑定给某次会话的原子操作 |
| **Hot Path（热路径）** | 池命中，申请 O(百毫秒) 完成 |
| **Cold Path（冷路径）** | 池空，需全新建 Pod，O(秒) 完成 |
| **Hibernate（休眠）** | 沙箱进入低资源占用状态但保留可恢复的执行上下文 |
| **Drain（排空）** | 有序回收某池/某节点上的空闲沙箱，用于维护 |
| **Reclaim（回收）** | 释放沙箱及其所有关联资源 |
| **Lease（租约）** | `coordination.k8s.io/v1` 对象，用于存活心跳与超时判定 |
| **Overcommit（超卖）** | `requests` 总和 > 节点可分配资源，依赖实际用量错峰 |
| **RuntimeClass** | K8s 原语，声明 Pod 使用的容器运行时（runc/kata-fc） |
| **Profile（画像）** | 一类沙箱的资源使用统计分布，用于生成规格档位 |
